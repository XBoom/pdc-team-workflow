# 代码仓调研方法论 · grep playbook（v1）

> **本文件是「深度分析四准则 · 准则 1 · 资料获取双轨制」的可执行 SOP**。
> 当调研组 B 需要 `git clone` 一个开源项目并精读源码时，按本 playbook 执行。

---

## 一、为什么需要这个方法论

### 核心矛盾

每个成熟开源仓库都有**几千到几万个文件**，但你只有 **1-2 小时**。

如果"试图理解整个仓库"，结果必然是：
- 90% 时间花在读无关代码
- 真正需要的答案反而被错过
- evidence-ledger 里的 src 引用全是模糊的（"看 README" / "查 docs"），C 闸门无法验证

### 解决思路

**不要试图"理解"仓库。要"从 N 个调研问题出发，去每个仓库里精确找到 N 个答案"**。

类比法医取证：不需要"读完整个人"，只需要找到那一处刀伤、那颗弹壳、那段血迹。每个 Read 的文件都必须能直接回答 plan 里的某个具体问题，并带**文件路径 + 行号 + 关键发现**。

---

## 二、4 步 SOP（总览）

```
Step 1 · 明确"我要回答什么"          ← 来自 A 计划员的问题清单
Step 2 · 从顶层结构找"代码集中区"    ← 5 分钟 ls
Step 3 · 用 2-3 个 grep 把概念映射到文件  ← 10 分钟精确制导
Step 4 · 亲自 Read 命中文件，**只读决策相关段**  ← 20-30 分钟取证
```

每步都有**时间盒**，超时说明方法论用错了（不要硬刚，及时回头看 Step 1）。

---

## 三、4 步详解

### Step 1 · 明确"我要回答什么"（2 分钟）

**不是"这个仓库好厉害我想读读"，而是"我必须回答 Q2 / Q11 / Q14，所以必须确认 X"**。

| 来源 | A 计划员写的 plan.md「问题清单」|
|---|---|
| 输出 | 每个调研问题对应的"必须确认的具体子问题"列表 |

**示例**：
- ❌ 错误："我要读懂 Dify"
- ✅ 正确："Q11 要确认 Dify 的流式输出是用 SSE 而不是 WebSocket；Q2 要确认 Dify 的 workflow 引擎是否能独立嵌入"

每个问题对应 **1-3 个具体子断言**，每个子断言要在仓库里找到证据。

### Step 2 · 从顶层结构找"代码集中区"（5 分钟）

```bash
# 1. 看仓库根目录
ls <repo>/

# 2. 找到最深的、文件类型最统一的子目录
ls <repo>/<candidate-dir>/

# 3. 确认这是代码集中区
ls <repo>/<candidate-dir>/ | wc -l
# 如果 ≥ 30 个同类文件（如 .py / .ts / .go），就是
```

**经验**：
- 开源项目的 README 第一节 + `ls -F` 看根目录 = 5 分钟内能找到代码集中区
- **不要**读 tests/、examples/、docs/、CHANGELOG、.github/ 这些目录
- 这些是"上下文噪音"，**不是证据**

### Step 3 · 用 2-3 个 grep 把概念映射到文件（10 分钟）

针对每个 Q 关心的概念，跑 grep 看哪些文件真正"持有这个概念的实现"。

```bash
# ✅ 正确：grep 类名/接口名/概念关键词
grep -rln "Anthropic" litellm/llms/ | head
grep -rln "class StateGraph" libs/langgraph/ | head
grep -rln "Checkpoint" libs/checkpoint/ | head

# ❌ 错误：grep 通用词
grep -rln "import" packages/ | head   # 命中太多，无意义
grep -rln "class" packages/ | head    # 同上
```

**关键原则**：
- grep 的关键词**直接来自 Step 1 的子断言**
- 每个 grep 命令必须能**直接映射到一个 Q 子问题**
- 跑 2-3 个 grep 就锁定 1-3 个文件，**不要贪多**

### Step 4 · 亲自 Read 命中 文件，**只读决策相关段**（20-30 分钟）

锁定文件后：

```bash
# 1. 看大小（> 1000 行的文件一定不从头读）
wc -l <file-path>

# 2. 找所有类/函数定义
grep -n "^class\|^def\|^export class\|^export function" <file-path>

# 3. 找 docstring/注释（往往在类定义顶部 5-15 行）
head -50 <file-path>
```

**只读与你的 Q 相关的 30-100 行**，记录：
- 类/函数签名
- 关键 docstring
- 与 Q 决策点相关的代码段（**带行号引用**）

**记录模板**（直接进 `code-readings.md`）：
```markdown
### 文件 N · `<绝对路径>:<行号范围>`
- **类/函数名**：`class StateGraph`（行 131）
- **关键发现**：...（引用具体代码片段）
- **回答的 Q**：Q2 checkpoint + 人环机制
```

## 四、证据记录规范（evidence-ledger 必备）

每条 `源码` 类断言必须满足：

| 字段 | 要求 |
|---|---|
| **路径** | **绝对路径**（如 `/tmp/requira-research/langgraph/libs/.../state.py`）|
| **行号** | 精确到行号范围（如 `:131` 或 `:131-156`）|
| **关键发现** | 1-3 句话 + 可选代码片段（≤ 30 行）|
| **回答的 Q** | Q 编号 + 子问题 |

**反例**（C 闸门必否决）：
- ❌ "看了 LangGraph 文档"（无文件 / 无具体段）
- ❌ "LangGraph 有 checkpoint"（无行号）
- ❌ `/path/to/file.py`（相对路径，C 无法验证）

## 五、真实示例（4 个最直观的 case）


## 六、效率优化（实战经验）

### 6.1 · clone 用 `--depth=1`

```bash
git clone --depth=1 https://github.com/<org>/<repo>.git /tmp/req-research/<repo>
```

只克隆最新一次提交，省时间、省空间。**只在你不需要看 git 历史时这样做**（调研几乎从不需要）。

### 6.2 · 每个仓库 Read 上限 5-7 个文件

即使问题很多，**对单个仓库 Read 不要超过 7 个文件**。理由：
- 时间预算（每个仓库 30 分钟）
- 调研的目的不是"穷尽"，是"找到证据"
- 真有更多问题时，再 clone 一遍或查官方 docs

### 6.3 · 用 `sed -n` 精准 Read 段

```bash
# 读 200-250 行
sed -n '200,250p' <file-path>

# 读全文（仅 < 200 行的小文件）
cat <file-path>
```

不要用 `head -1000` 这种模糊命令，**要精确到行号**。

### 6.4 · 用 sub-subagent 并行调研

主 B 把 8 个仓库拆给 4 个 sub-subagent 并行，每个 sub-subagent 负责 2 个仓库。这样 8 个仓库 30 分钟跑完，而不是 60 分钟。

### 6.5 · 透明声明 clone / 替代来源

如果某仓库 clone 失败（如网络问题、submodule 失败），**必须在 code-readings.md 顶部声明**，并用 WebSearch + WebFetch 替代。这是诚信，不是掩盖。

## 七、C 闸门验证 SOP（C 核查员用）

C 必须**亲自 sed 抽查**每条 `源码` 类断言：

```bash
# 抽查示例（来自 check.md 真实工作）
ls /tmp/requira-research/langgraph/libs/langgraph/langgraph/graph/state.py
sed -n '128,135p' /tmp/requira-research/langgraph/libs/langgraph/langgraph/graph/state.py
# 验证 B 引用 "state.py:131" 真的有 StateGraph 类

sed -n '175,180p' /tmp/requira-research/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py
# 验证 B 引用 "base/__init__.py:177" 真的有 BaseCheckpointSaver 类
```

**5 条抽查全中 = 闸门放行**。任何 1 条行号不精确 → 打回 B 修正。
