# 项目交付团队 · 蓝图 v2（深度分析标准 / P-D-C 串行闸门流水线）

> 在 v1「7 职能组 × 3 人 P-D-C + 主控」串行闸门流水线基础上，针对「不够详细 / 怕杜撰 / 要可落地实现 / 要多层报告」四类诉求，新增 **深度分析四准则**。
> team-lead 由 WorkBuddy 主控 Agent 担任。运行模型不变：按任务选组 → 单组激活 → P-D-C 闭环 → C 闸门放行 → 流转下组；但在每个组内贯穿「资料可溯、原理透彻、设计可落地、报告可下钻」。

---

## 一、运行模型（核心规则，不变）

1. **任务路由**：主控收到任务后，判断需要哪些职能组、什么顺序——不必唤醒全部组。
2. **单组激活**：同一时刻**只激活一个职能组**（3 人），其余组待命。省资源、易控进度。
3. **组内 P-D-C 闭环**：A 计划 → B 执行 → C 核查；C 不通过则打回 B（或退 A 修订），**不放行**。
4. **闸门流转**：当前组 C 签字放行后，产物交给下一组的 A，唤醒下一组；如此串行推进。
5. **主控汇总**：最后一组放行后，主控汇总交付，Boss 验收。

```
[任务] → 主控选组+排序 → 唤醒组①(A→B→C) ──C放行──▶ 唤醒组②(A→B→C) ──▶ … ──▶ 主控汇总 → 你验收
                                  ↑ 不通过打回 B/A，同一组内闭环
```

> **v2 新增约束**：任何「分析 / 原理 / 报告」类任务，第一组必须是**资料与代码调研组**（先搜后析、且拉代码到本地）；后续各组产物都必须可追溯到调研组给出的来源。

---

## 二、任务 → 职能组 映射（按需选组，不强制全员）

| 任务类型 | 唤醒的职能组（顺序） | 通常跳过 |
|----------|----------------------|----------|
| 产品 / 技术原理分析报告 | **调研(含代码考古)** → 技术与架构分析 → 内容撰写 → 设计可视化 → 质检 | 规划架构、开发执行 |
| 软件开发 / 新功能 | 规划架构 → 开发执行 →（测试工程）→ 质检 | 调研（需求已明时） |
| 技术文档 / PRD | 规划架构 → 内容撰写 → 质检 | 开发、设计 |
| 营销方案 / 路演 PPT | 调研 → 内容撰写 → 设计可视化 → 质检 | 开发、数据分析（轻量时） |
| 上线 / 增长活动 | 运营增长 → 设计可视化 → 内容撰写 → 质检 | 开发、规划 |
| 合同 / 合规审查 | 法务合规 → 质检 | 其余 |

> 例：你说「构建产品分析报告」→ 主控只唤醒 **调研、技术与架构分析、内容撰写、设计可视化、质检** 五组，**开发执行组不唤醒**。

## 三、深度分析四准则（v2 核心新增）

> 这四条是 v2 相对 v1 的全部增量，作为每个组的硬执行标准，写入各组 brief。

### 准则 1 · 资料获取双轨制（先搜后析，且拉代码到本地）
- 任何分析类任务，**第一步必为资料获取**，分两条轨道并行：
  - **轨道 A 网络检索**：WebSearch + WebFetch 拿官方文档、论文、博客、issue、对标项目。
  - **轨道 B 代码考古（关键新增）**：对开源项目，`git clone` 到 `outputs/<任务>/_src/`，用 Read / Grep / Bash 读**真实源码、commit、测试**，提取机制。**禁止只靠 WebFetch 摘要就下结论**。
- 产物：`outputs/0X-调研/sources.md`（来源清单：URL / 本地路径 / commit SHA）+ 结构化资料卡片。

### 准则 2 · 原理 → 方案详细设计 → 可落地（深度递进）
- 对每一个技术机制，分析组必须给出**三级深度，缺一不可**：
  1. **原理层**：它解决什么问题、思想来源、形式化描述。
  2. **方案详细设计层（新增）**：数据结构、模块划分、关键函数签名、算法步骤 / 伪代码、配置项、与其他模块的交互契约。读者照此能自己实现。
  3. **可落地层**：依赖、边界条件、性能 / 失败处理、与本地代码的实测对照。
- 内容组把「方案详细设计」作为**独立章节**嵌入，而非只讲概念。

### 准则 3 · 反杜撰与证据台账（可追溯）
- **每条事实断言必须带出处**，格式 `[src: 路径:行号]` 或 `[src: URL]`。
- 调研组维护 `evidence-ledger.md`（断言 → 来源映射表）。
- 无法确证的内容一律标注「推测 / 待验证」，不得伪装成事实。
- 质检组 C 的**硬性放行项**：无无据断言、无伪装事实、来源可复现。

### 准则 4 · 多层报告结构（可下钻）
- 内容组 A 必须规划**至少 3 层**的目录树：篇 → 章 → 节 →（子节 / 深读框）。
- 每个章可再细分；对难点设「深读」折叠块，做到「近乎透彻」。
- 产物形态：一份带多级目录、可点击跳转、关键章有「原理 + 设计 + 代码对照」的 HTML / 文档。

## 四、核心职能组（增强 brief，结构不变）

> 通用 Brief 骨架：`背景：<…> 已知：<…> 你要做：<计划/执行/核查> 标准：<…> 交付：outputs/0X-角色/<plan|draft|check>.md` —— v2 起所有 brief 追加「深度四准则」要求。

**[增强] ① 资料与代码调研组**（A=Plan，B=Explore/general-purpose，C=general-purpose）
- A 定检索维度 + 本地代码目标仓库；B **同时**做网络检索 + `git clone` 本地读码（轨道 A+B），出 `sources.md` + 资料卡片；C 核对维度覆盖、来源可靠、**代码确已拉取并精读**、无关键遗漏。

**[增强] ② 技术与架构分析组**（A=Plan，B=general-purpose，C=general-purpose）
- A 定分析口径 + 详细设计清单；B 基于真实源码 / 资料，对每个机制产出「原理 + 方案详细设计 + 可落地」三级，并附代码片段与文件路径；C 核对分析有据、设计自洽、层级达标。

**③ 规划架构组**（A=Plan，B=general-purpose，C=general-purpose）
- A 定方案框架 / 里程碑 / 依赖 / 风险；B 细化产出方案；C 查完整性、可行性漏洞、风险遗漏。（实现类任务触发）

**④ 开发执行组**（A=Plan，B=general-purpose[Bash/code]，C=general-purpose）
- A 定实现方案 / 模块 / 接口 / 验收标准；B 写代码搭页面跑命令；C 查是否符合计划与验收、边界异常漏洞。（实现类任务触发）

**[增强] ⑤ 内容撰写组**（A=Plan，B=content-creator，C=general-purpose）
- A 定**多级目录树（≥3 层）** + 受众 + 必含「原理 / 设计 / 代码对照」章；B 成稿（含深读块、跳转锚点）；C 核对齐目录树、事实一致、证据齐全、无遗漏。

**[增强] ⑥ 设计可视化组**（A=Plan，B=content-creator，C=general-purpose）
- A 定版式 / 配色 / 信息层级 / 页数；B 做图件（架构图 / 流程图 / 曲线），**图件需标注数据来源**；C 查规范、信息准确、重点突出、来源可信。

**[增强] ⑦ 质检组**（A=Plan，B=general-purpose，C=general-purpose）
- A 定总清单（**含反杜撰硬项**）；B 全链路检查；C 复审覆盖 + **逐条核验 evidence-ledger**，出终审报告（含「无据断言零容忍」结论）。

## 五、可选职能组（按需唤醒，补全产品全生命周期）

核心 7 组覆盖「调研→分析→规划→开发→内容→设计→质检」主线，要覆盖产品**所有**任务，还需以下可选组，由主控按任务唤醒：

| 可选组 | A 计划 | B 执行 | C 核查 |
|--------|--------|--------|--------|
| 测试工程组 | 测试计划 / 用例标准 | 写跑单元·集成·自动化测试 | 覆盖率与遗留漏洞核查 |
| 运营增长组 | 增长策略 / 指标 | 投放 / 活动 / 内容运营 | ROI 与数据对齐核查 |
| 法务合规组 | 合规清单 | 审合同 / 隐私 / 政策 | 风险与遗漏核查 |
| 运维 / SRE 组 | 部署与监控方案 | 实施 CI/CD / 监控告警 | 稳定性与故障预案核查 |
| 商业化组 | 商业模式 / 定价 | 销售 / 报价执行 | 测算与合规核查 |

## 六、产物清单（v2 新增，分析类任务最低交付）

每个分析类任务在 `outputs/` 下至少含：

- `0X-调研/sources.md` —— 来源清单（URL / 本地路径 / commit SHA）
- `0X-调研/evidence-ledger.md` —— 断言 → 来源台账
- `0X-分析/<机制>-design.md` —— 各机制「原理 + 方案详细设计 + 可落地」三级文档
- `0X-撰写/toc.md` —— 多级目录树
- `0X-撰写/draft.html` —— 多层报告（含深读块、跳转锚点、原理/设计/代码对照）
- `0X-质检/check.md` —— 含反杜撰逐条核验的终审报告

---

## 七、协作协议（单组激活版）

- **任务看板**：主控 `TaskCreate` 建任务，当前组 `TaskUpdate` 标 A 计划 → B 执行 → C 核查；下一组唤醒后同样流程。
- **产物编号**：`outputs/0X-角色/{plan,draft,check}.md`，闸门流转时整组产物一并交接。
- **协调**：组内用 `SendMessage`（C→B 打回 / C→A 退计划）；跨组由主控在闸门处交接。
- **规模优势**：同一时刻最多 3 个 teammate 在跑，资源友好、进度清晰。

## 八、启用示例（深度分析版 · 以 llm-wiki 为例）

1. 主控选组：调研(含代码考古) → 技术与架构分析 → 内容撰写 → 设计可视化 → 质检。
2. **调研组**：A 计划（检索维度 + clone 目标仓）→ B `git clone` 到 `_src/` + 网络检索，出 `sources.md` / `evidence-ledger.md` → C 核查放行（确认代码已精读）。
3. **分析组**：接调研产物，A 定详细设计清单 → B 对每个机制产出「原理+方案详细设计+可落地」三级，附真实代码片段 → C 核查放行。
4. **内容组**：A 规划 ≥3 层目录树 → B 成稿（深读块、跳转锚、原理/设计/代码对照）→ C 核查放行。
5. **设计组**：图件标注数据来源 → C 核查放行。
6. **质检组**：A 清单（含反杜撰）→ B 总检 → C 逐条核验 evidence-ledger → 终审报告。
7. 主控汇总成多层 HTML 报告，Boss 验收。

> 这套流程即 v2 标准。今后你给任意任务，主控都按此四准则执行；如需反复使用，可沉淀为可复用 Skill 一键拉起。
