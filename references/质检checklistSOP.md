# 质检 checklist SOP · C 闸门可执行流程（v1）

> **本文件是「P-D-C 串行闸门」中 C 核查员角色**的可执行 SOP**。
> 当任意流程的 B 提交产物需要 C 闸门时，按本 checklist 执行。

---

## 一、为什么需要这个 SOP

### 核心矛盾

SKILL.md §三·核心规则 3 说"C 闸门不放行就不能流转到下一组"，但 **C 到底怎么做、做到什么程度算放行**，没有标准化答案。

如果 C 走过场（只看 B 自检结果就放行），结果必然是：
- B 写的"8/8 全部通过"无人复核，错误向下游污染
- evidence-ledger 的 src 引用全凭 B 一面之词，最终报告失实
- 整个 pdc 流水线的"反杜撰"承诺破产

### 解决思路

**C 不是 B 的复读机，C 是 pdc 流水线的独立审计员**。

C 必须**亲自 grep + 亲自 sed + 亲自 Read**，用自己的眼睛验证 B 的产物。任何"我相信 B 说的对"的省略都是错的。

类比独立审计师：审计师不重做会计的工作，但必须**亲自抽凭、亲自盘点、亲自函证**。

---

## 二、C 闸门的 4 个核心动作

```
动作 1 · 文件存在性核查     (ls + wc -l)
   ↓
动作 2 · 模板完整性核查     (grep 章节标题 + 抽查模板字段)
   ↓
动作 3 · src 引用可溯性核查 (亲自 sed 抽查 ≥ 5 条)
   ↓
动作 4 · 一致性核查         (与上游产物对比，不允许擅自修改选型)
```

每一步都是 C **自己**跑，不能让 B 代劳。

## 三、checklist 模板（直接复制使用）

```markdown
### 维度 1 · 文件存在性与行数
- [ ] 实际 `ls` 所有声明的产物文件
- [ ] `wc -l` / `wc -c` 实际行数与字节数
- [ ] 对比 B 自报；如不一致标 ❌（说明 B 漏写或谎报）

### 维度 2 · N Q 覆盖完整性
- [ ] `grep -n "^### Q[0-9]" draft.md` 列出所有 Q 章节
- [ ] 验证 N Q 全部出现（如 Q1-Q13 共 13 个）
- [ ] 抽查 M 个 Q（建议 M=3，覆盖核心 Q + 边缘 Q）
- [ ] 每个抽查 Q 必须包含：候选 / 推荐 / 对比矩阵（≥4 行 × ≥3 列）/ 决策依据 ≥3 / 落点 / 死因

### 维度 3 · evidence-ledger 引用真实可溯
- [ ] 报告中 `[src: E{nnn}]` 总数与唯一 E-ID 数（用 `grep -oE "E[0-9]{3}" report | sort -u | wc -l`）
- [ ] 抽查 10 处引用（必须分布在不同 Q，不可集中在 1 个 Q）
- [ ] 亲自去 ledger 中验证每个抽查的 E-ID 是否存在
- [ ] 验证 E-ID 对应的「来源」字段（URL / 文件路径）是否真实可访问

### 维度 4 · git clone 项目实读（如适用）
- [ ] `ls /tmp/req-research/` 确认 K 个项目实际存在
- [ ] 每项目 ≥3 条「文件 + 发现 + 行号」记录
- [ ] 抽查 2 个项目的关键文件，亲自 `sed -n` 验证 B 引用的行号精确

### 维度 5 · WebFetch 覆盖（如适用）
- [ ] N URL 中至少 N-1 个被 WebFetch（B 自报 15，实际可能 14，要核对）
- [ ] 抽查 3 个 URL 的 WebFetch 记录：HTTP 状态 + 关键摘录 + 对应 Q

### 维度 6 · 风险盲区回应
- [ ] plan 第 X 节声明的 N 项风险盲区，B 在草稿中是否**显式**回应
- [ ] "显式" = 用段落或表格写出"我查过这个问题"或"我未覆盖，原因 Y"
- [ ] 抽查 M 项回应是否到位（M = min(N, 3)）

### 维度 7 · 与上游产物的一致性
- [ ] 抽查 X 个 Q（建议 X=3）的选型是否与上游产物一致
- [ ] **不允许** B 擅自修改选型
- [ ] 如有差异，必须有显式声明 + 主控校准说明
- [ ] 抽查 Q1 / Q5 / Q14 这种关键决策点的引用是否真实
```

**强制约束**：维度 1-4 必须全部 ✅，否则打回。维度 5-7 是补强维度。

## 四、5 个真实反例（避免走过场）

| # | ❌ 反例（走过场） | ✅ 正确做法 |
|---|---|---|
| 1 | "看了 B 的 check.md 自检说 8/8 通过" | "亲自 `grep -n '^### Q[0-9]' draft.md` 实际数 Q 数" |
| 2 | "src 引用看起来都对" | "亲自抽 10 条 `[src: Ennn]`，去 ledger 验证 E-ID 是否存在 + 行号是否精确" |
| 3 | "B 说 Read 了 41 个文件" | "亲自 `ls /tmp/req-research/` 确认 8 个项目实际存在" |
| 4 | "B 说 sed 了 5 条行号" | "亲自重跑那 5 条 `sed -n`，验证行号内容真实（不是 B 编的）" |
| 5 | "Q9 推荐有变化，但 B 说合理" | "Q9 推荐变化必须在 draft.md 顶部显式声明 + 主控校准声明引用" |

**走过场是 pdc 流水线最大的失败点**。即使时间紧，5 个核心动作也不能省。

## 五、3 档判定标准（质检报告怎么写结论）

```
终审放行（9-10 ✅）
   ├─ 适用：所有维度全部达标
   ├─ 允许：可附"非阻塞建议"作为下次迭代改进
   └─ 下游：可立即接力

放行+建议（7-8 ✅）
   ├─ 适用：核心维度（1-4）达标，维度 5-7 有轻微瑕疵
   ├─ 要求：明确写出瑕疵 + 后续 fix 工作量（如"5 秒 fix"）
   └─ 下游：可接力，建议清单在 M2/M3 兑现

打回（≤6 ✅）
   ├─ 适用：核心维度（1-4）任何一项不达标
   ├─ 要求：列出具体 + 怎么修（不要只说"不达标"）
   └─ 下游：B 重新做，C 重审
```

**不允许"中间档"**（如 8.5 ✅ → 标"放行"但不写建议）。判定要明确，否则下游不知该不该接力。
